# Web architecture

The web version reproduces the native mobile application in the browser: static Astro pages, one per tab, wrapping vanilla JavaScript views:

- **Pages** (`src/pages/<tab>/index.astro`, built by Astro): each wraps [src/layouts/Base.astro](../../src/layouts/Base.astro) (head, the four mount points, the inline theme script) and sets `<body data-view>`; four tabs: map, weather, forecast, safety (`/profile/` redirects to `/map/`). [src/main.js](../../src/main.js) mounts the header, bottom nav, bottom sheet and the view `data-view` names, and installs global `error` and `unhandledrejection` loggers. `store.setTab` in [src/state.js](../../src/state.js) navigates to `/<tab>/`; selections handed to the map travel in its URL ([src/scripts/handoff.ts](../../src/scripts/handoff.ts)). `store` persists language, theme, map settings, vario rate and logbook to `localStorage` (`shv_*` keys, [src/scripts/settings.ts](../../src/scripts/settings.ts)) and the checklist to `sessionStorage`.
- **Views** ([src/views/](../../src/views/)): `MapView` (Leaflet map, layers, obstacles), `ForecastView` (text forecasts, outlooks, soundings, isobar charts).
- **Ported pages**: the safety page (DABS, checklist, logbook, variometer) is `.astro` markup in [src/components/safety/](../../src/components/safety/), filled in the `view` slot of `Base.astro`, with its behaviour in [src/scripts/safety/](../../src/scripts/safety/) (`page.ts` attaches the handlers; the rest are pure, tested modules). The weather page (station pairs, live stations, webcams) follows it in [src/components/weather/](../../src/components/weather/) and [src/scripts/weather/](../../src/scripts/weather/), with its charts in [src/scripts/charts/](../../src/scripts/charts/) and its tab and pair in the URL (`/weather/?tab=webcams&pair=GVE_GUT`). Its words come from the dictionaries through `data-t` attributes ([src/scripts/i18n/text.ts](../../src/scripts/i18n/text.ts)), so the language switch still works without a reload, and every stored or upstream value in an HTML string goes through `escapeHtml` ([src/scripts/escape.ts](../../src/scripts/escape.ts)). The other views follow this pattern as they are ported.
- **Data client**: [src/scripts/api.ts](../../src/scripts/api.ts) (`ShvApi`, typed against [src/scripts/types.ts](../../src/scripts/types.ts)) is the only module that calls `fetch`; it caches the GIS datasets in memory.
- **Translations**: [src/i18n/](../../src/i18n/) holds `de`, `fr`, `it` and `en`, read through `store.t`. Many strings in the legacy views are still hardcoded German; a ported page has none.
- **API** ([functions/api/](../../functions/api/), Cloudflare Pages Functions): the `/api/*` routes in [data-queries.md](data-queries.md), one-line adapters over [src/scripts/upstream/](../../src/scripts/upstream/). Shared shapes, and the Functions' `Context` type, are in [src/scripts/types.ts](../../src/scripts/types.ts).
- **Dev launcher**: [scripts/dev.ts](../../scripts/dev.ts) runs `wrangler pages dev public` on `8788`, which compiles `functions/` without a build, and `astro dev` on `4321`, which proxies `/api` to it ([astro.config.mjs](../../astro.config.mjs)).

## Member login

There is none. The copy-paste PKCE login against SHV Keycloak reused the official Android app's public client; it went with Express (PR9) and the Profile tab (PR13). The header links to the SHV member portal, and `purgeLegacyAuth` clears the session id and profile old versions stored. How the official app's login works is in [reference/shv-native-app.md](../reference/shv-native-app.md); the design to use if login returns is in the [migration plan](../plan/2026-11-23-astro-cloudflare/target.md#auth-deferred).
