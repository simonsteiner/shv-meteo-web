# Data queries: direct from the browser or through a Function

The browser calls an upstream directly when it allows CORS and the payload is light. Anything else goes through a Pages Function in [functions/api/](../../functions/api/): an upstream that refuses browsers (weather-ws-prod and webcam-prod answer 403 to an `Origin` header; the text forecast host sends no CORS header), heavy data, or maths over several stations. Each Function is a one-line adapter over [src/scripts/upstream/](../../src/scripts/upstream/), where the rules live and the tests run:

- **[routes.ts](../../src/scripts/upstream/routes.ts)**: each route's fixed upstream URL, TTL, timeout and German error body. No request picks a host.
- **[params.ts](../../src/scripts/upstream/params.ts)** and each route's `parse` in [routes.ts](../../src/scripts/upstream/routes.ts): path parameters decoded once (`params.ts` holds the helpers, `parse` the rules of its own route); a timeseries id must match `STATION_ID` (`handoff.ts`, which the map's `?station` and `?webcam` use too): `<provider>:<id>` without `/` (else 400 "Ungültige Stations-ID"); the text forecast's language is `de`, `fr` or `it`, anything else `de`.
- **[fetch.ts](../../src/scripts/upstream/fetch.ts)**: the User-Agent `shv-meteo-web (+https://github.com/simonsteiner/shv-meteo-web)`, never an `Origin`, and one deadline (the route's timeout) for the whole answer: a stall before the headers rejects the call, a stall in the body errors the body, so the parsing routes (Foehn, sounding) fail into their stale copy or 503 and a streamed route's half-sent body is never cached. The edge cache's copy reads the body at upstream's speed, so a slow browser doesn't count against the deadline.
- **[respond.ts](../../src/scripts/upstream/respond.ts)**: a 200 streams upstream's body unparsed with upstream's `Content-Type` and `Cache-Control: max-age=<TTL>`, nothing else from upstream, and a body that stalls after that is cut off at the deadline; a timeout or network error before the headers, any upstream non-2xx or a 200 whose `Content-Type` isn't JSON (a maintenance page) is a 503 with the route's error body and `no-store`, and is never cached. Each 200 is kept in the edge cache (`caches.default`) for a day: a copy younger than the TTL is served without calling upstream (`x-cache: hit`), an older one is refetched and still served when the refetch fails (`x-cache: stale`, `no-store`), if its body still looks like JSON: a copy up to about 200 KB must parse, a larger one (measurements, about 2 MB) only needs its first and last non-whitespace bytes to be a matching `{`/`}` or `[`/`]`, which keeps the parse under `target.md`'s 200 KB and still catches a truncated body. A copy that fails the check is dropped and the route answers its 503; one that can't be read is kept and the route answers its 503. Only that fallback is checked, so a fresh hit costs nothing. PR9's spike, below, showed `pages.dev` keeps these copies.

## Data flow

| Resource | Upstream | Path | Why | What happens on the way |
| :--- | :--- | :--- | :--- | :--- |
| **Swisstopo and OSM tiles** | `wmts.geo.admin.ch`, `*.tile.openstreetmap.org` | **Direct** | Public tile caches with CORS. | None; Leaflet loads the images. |
| **Flying sites, airspaces, wildlife zones** | `public/data/*.geojson`, falling back to `shv-app-static-prod.ubmeteo.io` | **Direct** | Snapshots served by Pages; the CDN allows CORS. | None: the local copy first, the live CDN only if it fails. |
| **Outlook frames and index** | `static-prod.ubmeteo.io/v1/animation/switzerland/days_overview.json` and its WebP frames | **Direct** | CORS `*`. | None; `ShvApi.getOutlooks` fetches `OUTLOOKS_URL` ([src/scripts/api.ts](../../src/scripts/api.ts)). |
| **Isobar chart** | `shv-app-ws-prod.shv-app.ch/v1/text/isobaren/{lang}.svg` | **Direct** | Used only as an `<img>`, which needs no CORS and never runs the SVG's scripts. | `isobarenUrl(lang)` maps `en` and anything unknown to `de`. |
| **DABS card** | None | **Browser** | Today's date and fixed Skybriefing links. | `buildDabs(now)` in [src/scripts/api.ts](../../src/scripts/api.ts), dated in Swiss time. |
| **Live ground stations (`/api/measurements`)** | `weather-ws-prod.ubmeteo.io/v1/measurements/current` | **Function** | 403 to browsers; 2.2 MB. | Always the Alps bbox (lat 43.5 to 49.5, lon 4 to 16) and the nine parameters the map and the weather page read (`parameters=`: wind speed, direction and gust, `temperature`, `dew_point`, `relative_humidity`, which include their 2 m variants, and `pressure_msl`, `pressure_standard_msl`, `pressure_surface`), no query accepted; 12 s timeout; `max-age=60`. Unfiltered it was 3.1 MB and 4,179 stations; filtered, 2.2 MB and 3,754, the 425 dropped reporting only values we don't show (precipitation, pollen, radiation, snow depth). |
| **Station timeseries (`/api/measurements/timeseries/:id`)** | `weather-ws-prod.ubmeteo.io/v1/measurements/timeseries/{id}` | **Function** | 403 to browsers. | Fixed parameter list `wind_speed,wind_direction,wind_gust,temperature,dew_point,pressure_msl,relative_humidity` (a station without dew point just leaves that series out), no `?parameters=`, and the last 24 hours only (`start=`, rounded down to the minute so upstream's cache can answer, as for Foehn); the edge-cache copy is keyed by station alone, so the moving `start` adds no copies. Upstream's default was 14 days: on 2026-11-24, KLO went from 548 KB (82 KB gzip) and 14,084 points to 39 KB (6 KB gzip) and 1,001, a Holfuy station (`holfuy:1086`, one-minute values) from 3.1 MB (375 KB gzip) and 80,120 points to 211 KB (25 KB gzip) and 5,576. `max-age=180`. |
| **Webcams (`/api/webcams`)** | `webcam-prod.ubmeteo.io/v1/webcams/overview` | **Function** | 403 to browsers. | Fixed Swiss bbox (west 5.9, south 45.8, east 10.5, north 47.8); `max-age=120`. |
| **Text forecast (`/api/meteo/text-forecast/:lang`)** | `shv-app-ws-prod.shv-app.ch/v1/text/forecast/{lang}.json` | **Function** | No CORS header. | `de`, `fr`, `it`, else `de`; a malformed escape is a 400. `max-age=900`. |
| **Foehn station pairs (`/api/foehn`)** | `weather-ws-prod.ubmeteo.io`: the current measurements in one call per parameter (`pressure_standard_msl`, QNH, for the pressure pairs, `temperature` for Pilatus/Matro), each limited by `parameters=` to that value and to the box around its stations (`STATION_POSITIONS` in `pairs.ts`), about 20 KB each, and the pair's two timeseries from 25 hours back (`start=`, rounded down to the minute so upstream's cache can answer) | **Function** | Maths over several stations. | [src/scripts/foehn/](../../src/scripts/foehn/): the four pairs' differences and alert levels, their GeoJSON, and `?pair=` (unknown: `KLO_LUG`) adds that pair's 24 h history, labelled in Swiss time. A station missing from its answer drops its pair (logged); any failed measurements call is the 503 "Föhndaten vorübergehend nicht erreichbar"; a failed or empty series only empties `history`. `max-age=60`, cached per pair. |
| **Sounding station catalogue** | `public/data/previtemps_stations.json` | **Static** | 107 stations, served by Pages. | `ShvApi.getPrevitempsStations` loads the file; no Function. |
| **Sounding forecast (`/api/meteo/previtemps/forecast/:name`)** | `weather-ws-prod.ubmeteo.io/v1/point-data/<model>/runs`, then `/<run>/<point>?parameters=` with the six series in one answer (about 160 KB) | **Function**, levels in the **Browser** | Point data answers 403 to an `Origin` header; the level maths stays out of the Function's CPU. | The station's ICON grid point comes from `src/data/previtemps_grid.json` (`npm run grid`, ICON-CH1 before ICON-CH2); a name outside the catalogue is a 404 "Unbekannte Sondierungsstation", matched case-insensitively, `/` allowed. The Function takes the newest run, passes over one with a series missing, a column whose pressure falls less than 300 hPa from the ground to the model top, or no complete level (`pointProblem` in [sounding.ts](../../src/scripts/emagram/sounding.ts)), and answers upstream's text, parsed for that check but not re-serialised, inside `{station, run, point}`. `ShvApi.getEmagramForecast` turns it into levels up to 550 hPa (dew point, wind, lapse rate; [levels.ts](../../src/scripts/emagram/levels.ts)). Only the newest two runs are tried; neither usable is the 503 "Sondierung vorübergehend nicht erreichbar". `max-age=1200`. |
| **BAZL obstacles** | `public/data/obstacles/<tier>/<cell>.json`, built from `shv-app-static-prod.ubmeteo.io/v1/obstacles/bazl.geojson` | **Static** | 128 MB dataset: too big for a Function or the browser whole. | `npm run obstacles` ([scripts/obstacles.ts](../../scripts/obstacles.ts)) writes one tier per LOD cut point (z7, z9, z10, z11, z12, z13), each holding every feature visible from its zoom, in cells of 1, 0.5 or 0.25 degrees; a cell over 2 MB is split in four. `ShvApi.getObstacles` reads `index.json` once, loads the cells the view touches (of a split cell, only the quarters it touches, whose box follows from the name `<cell>.<i>`), dedupes by `_uid`, cuts to the view and caps at 2000 ([src/scripts/obstacles/](../../src/scripts/obstacles/)). The cells read last are kept up to 32 MB of JSON, and a cell still loading when the map moves on keeps loading as long as the next view wants it too (`recent.ts`). `deploy.yml` rebuilds them daily. |
| **Member login (`/api/auth/*`)** | SHV Keycloak | **Dropped** | Reused the official app's public client. | Gone with the Profile tab; the header links to the SHV member portal. |

Express and its Python parcel analysis are gone (PR9), and so is `/api/obstacles` (PR12). The routes nothing called (`/api/health`, `/api/emagram/calculate`, `/api/meteo/previtemps/sounding*`, `/api/obstacles/tiles/*`) were not ported.

## Spike: edge caching and CPU on pages.dev (PR9, 2026-11-23)

Run as branch previews of project `shv-meteo`: PR9's spike Function (`spike`), then the stack head with the real routes (`stack`). CPU times are Cloudflare's own, from the GraphQL analytics (`pagesFunctionsInvocationsAdaptiveGroups`) for the spike and from `wrangler pages deployment tail` per request for the real routes; `Date.now()` inside a Function stands still during compute, so it can't time it.

- **Edge cache: works.** `caches.default` on `pages.dev` kept the copy: the first request said `x-cache: miss`, requests 46 s and 2 min 17 s later said `hit` with the first one's `x-fetched-at`. On the stack preview every route answered `miss` first and carried its `max-age`.
- **Params: one undecoded segment.** `/api/_spike/Disentis%2FMust%C3%A9r` gave `params.path = ["Disentis%2FMust%C3%A9r"]`, as `wrangler pages dev` does locally, so `[name].ts` with `decodeURIComponent` (`params.ts`) is right, and `Disentis%2FMust%C3%A9r` answers 200 on the preview.
- **CPU: over the 10 ms Free limit for Foehn.** The spike route (Swiss-bbox measurements and two six-parameter series parsed) took p50 10.6 ms, p90 14.9 ms, p99 21.4 ms over 28 requests. The real `/api/foehn`, freshly computed (each pair once a minute, 12 requests), took 8 to 29 ms, median 16.5 ms; served from the edge cache it takes about 1 ms. Every request succeeded, but the Free plan does not promise that above 10 ms. Most of it is parsing the 0.8 MB Swiss measurements for eight stations: a ±0.01° box around each station returns about 2 KB holding it, and each pair's one-parameter series is about 80 KB. A fresh sounding (`Disentis/Mustér`) took 13 ms. Fixed by filtering the calls by parameter and box (about 40 KB of measurements and 12 KB of series); the result is under "Foehn with filtered calls" below.
- **Soundings: an upstream outage during the run.** From some time after 09:31 UTC upstream's point-data service served no data for any model: `/runs` kept updating (DWD's to 09 UTC), but every point of every listed run, and of the eight runs before, answered 404 "<model>:TEMPERATURE:<run> not available", whatever the User-Agent. Six stations (Beggingen, Zürich, Buochs, Schiers, Disentis/Mustér, Interlaken) still answered 200, but only from Cloudflare's cache (`cf-cache-status: HIT`, `Cache-Control: max-age=7776000, immutable`, last modified 09:31 UTC); a query string that skips the cache gives the same 404. The official app (1.1.0, decompiled) makes the same anonymous calls (`/runs`, then `/v1/point-data/<model>/<run>/<parameter>/<point>` for the nearest point of the zoom-10 grid tile within 20 km), uses only runs with every parameter present and otherwise shows "No complete emagram data available", so it fails the same way; there is no other source to switch to. The Function's 503 is the right answer while upstream is down. By 17:30 UTC upstream was back with `/runs` listing `[12Z, 06Z]`, newest first, the 12Z run complete and 06Z gone (404), but the Function still took the list's last run and kept answering 503. It now takes the newest run and falls back to the one before only when a series is missing ([fetch.ts](../../src/scripts/emagram/fetch.ts)); on a preview every one of 16 stations then answered 200 (34 time steps, 80 levels). A fresh sounding took 6 to 25 ms CPU, median 15 ms (9 requests), over the Free plan's 10 ms; the result after the fix is under "Soundings built in the browser" below.

### Foehn with filtered calls (2026-11-23)

`/api/foehn` now asks upstream only for what the report reads: `measurements/current` once per parameter with `parameters=` and the box around that parameter's stations (`pressure_msl`, 20 KB; `temperature`, 20 KB) and each series from 25 hours back (`start=`, 6 KB rather than 14 days in 76 KB). On a branch preview, 16 fresh reports took 3 to 13 ms CPU, median 5.5 ms (15 under 10 ms), against 8 to 29 ms before, with the same output. Eight per-station boxes were tried first and took a median of 10.5 ms: each upstream call costs CPU too. Details in [the research note](../research/2026-11-23-soundings-and-foehn-sources.md).

### Soundings built in the browser (2026-11-23)

Measured on branch previews, 20 fresh soundings each, CPU from `wrangler pages deployment tail`:

| Version | Upstream calls | Answer | CPU (median, range) | Over 10 ms |
| :--- | :--- | :--- | :--- | :--- |
| Levels in the Function, one call per series | 7 | 325 KB | 15 ms, 6 to 25 (9 requests) | 5 of 9 |
| Same, without `levelIndex` and `timeIso`, which nothing read | 7 | 278 KB | 6.5 ms, 5 to 14 | 4 |
| Same, the six series in one call | 2 | 280 KB | 6.5 ms, 3 to 15 | 3 |
| Point data passed through, levels in the browser | 2 | 162 KB | 3 ms, 2 to 7 | 0 |

The cost was the level maths and writing its JSON, not the calls. For six stations, the browser's sounding from the passed-through data matched the old Function's answer exactly (less the two dropped fields). Building it takes about 2 ms in Node.

The same evening upstream's ICON-CH1 and ICON-CH2 runs held nonsense columns: all 80 levels of a point, ground to 22 km, at about one pressure and temperature (786.7 to 787.0 hPa and 273 K at Interlaken, 526 to 562 hPa at Scuol), while `height_half_level` ran from 22,000 m down to the ground as it should. The check (`pointProblem`) rejects every one of the 107 stations' points, so the page shows its error rather than a flat chart; DWD's ICON-D2 and ICON-EU answered 404 for every listed run.

## Spike: BAZL vector tiles (PR12, 2026-11-23)

Upstream serves the dataset as MVT tiles (`shv-app-static-prod.ubmeteo.io/v1/obstacles/tiles/bazl/{z}/{x}/{y}.pbf`, CORS `*`), but only at z6, z9 and z12. Decoded and compared with `bazl.geojson` against the LOD rules:

| Tile | Size (gzip on the wire / decoded) | Zooms it would serve | Features visible there | Missing from the tile |
| :--- | :--- | :--- | :--- | :--- |
| `6/33/22` (all of Switzerland) | 2.4 MB / 8.4 MB, 97,874 features | z7, z8 | 8,808 | 667: the tile holds no points at all, so every tall or marked mast, crane, stack and windmill is gone |
| `9/267/180` (Bernese Oberland) | 0.34 MB / 1.1 MB, 11,713 features | z9 to z11 | 1,679 / 3,046 / 11,533 | 0 |
| `12/2137/1445` (Interlaken) | 6 KB / 17 KB, 184 features | z12, z13 | 82 / 184 | 0 |

Every tile feature has a stable `id` and carries `obstacleType`, `marking`, `styleId`, `maxHeightAgl`, `small`, `lighting`, `topElevationAmsl`, `sourceId` and `airport`. The tiles fall short at z7 and z8 (the map shows obstacles from z8), so PR12 took the shard path. A later change could read the z9 and z12 tiles for z9 and up and keep shards only for the overview. A wider check on 2026-11-24 (every z9 tile, 400 z12 tiles) found them 99.9% complete but a z9 tile carries z11 detail, so a z9 view would read about 3 times the bytes the shards cost and a z11 view about as much; the shards stay ([research note](../research/2026-11-24-obstacle-vector-tiles.md)).
